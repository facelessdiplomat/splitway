## AppRouting

### M4-01. Сопоставление приложений и решение по потоку
`shared` (используется на macOS) · L · зависит от: M1-10, M1-02

**Сделать:** в `AppRouting` Core:
- `SourceApplication` — что известно о процессе: signing identifier, Team ID, путь исполняемого файла (любое поле может отсутствовать);
- `ApplicationMatcher` — компилируется из `ApplicationSelection`: хэш-набор signing identifiers с привязкой к Team ID и отсортированный список префиксов путей; O(1) по идентификатору;
- `FlowDescriptor` — источник, адресат (IP или имя), порт, транспорт;
- `FlowRoutingDecider` — политика + matcher + `AllowedIPs` + готовность туннеля + наличие IPv6 в туннеле → `.tunnel` / `.direct` / `.block`;
- `RoutingPolicySnapshot` — компактная `Codable`-форма для передачи в расширение.

**Тесты сначала:** табличные тесты решения: приложение выбрано или нет; хелпер выбранного приложения; совпал идентификатор, но не Team ID (подмена) → `.direct`; адресат вне `AllowedIPs` → `.direct`; туннель не готов при `.block` и `.bypass`; IPv6-адресат без IPv6 в туннеле → `.block`. Тест производительности: 1 000 000 решений укладываются в бюджет, зафиксированный в тесте.
**Готово, когда:** решение детерминировано и не выделяет память на горячем пути (проверка в Instruments → Allocations).

## Движок в режиме netstack

### M4-05. `usernet`: WireGuard поверх gVisor netstack
`macOS` · L · зависит от: M2-03, SP-3

**Сделать:** Go-пакет `usernet`: устройство через `netstack.CreateNetTUN(addresses, dns, mtu)`; `DialTCP` с таймаутом; UDP-сокеты на адресата; резолвинг имён через DNS туннеля; на каждое соединение — горутина чтения с callback наружу и кредитный backpressure (Swift подтверждает обработанные байты); режимы закрытия (запись, чтение, полностью).
**Тесты сначала:** Go-тесты с двумя устройствами в процессе: echo-сервер внутри netstack пира, TCP и UDP туда и обратно, half-close, закрытие во время записи, 1000 параллельных соединений. Бенчмарки пропускной способности.
**Готово, когда:** тесты проходят без утечек горутин, бенчмарк не хуже результата SP-3.

### M4-06. Мост и адаптер `UserspaceNetworkEngine`
`macOS` · M · зависит от: M4-05

Для тестов — функция `tc_test_start_loopback_peer`, собираемая только с build tag `testpeer`: поднимает в процессе второй WireGuard-пир с echo-сервером.
**Тесты сначала:** Swift-интеграционные тесты через loopback-пира: TCP echo, UDP echo, закрытие, ошибка подключения к закрытому порту.
**Готово, когда:** Swift-тесты проходят в `Scripts/check.sh` на macOS (без системного расширения).

## TransparentProxy

### M4-07. Политики ретрансляции (Core)
`macOS` · S · зависит от: M4-01

**Сделать:** `RelayPolicy` (размеры буферов, таймауты подключения и простоя), `UDPAssociationTable` (ассоциации по адресату, истечение по простою), `HostnameResolutionPolicy` (когда использовать `remoteHostname`, а когда IP).
**Тесты сначала:** истечение ассоциаций с `FixedWallClock`; выбор имени или IP; лимиты числа ассоциаций.
**Готово, когда:** вся логика без NetworkExtension покрыта тестами.

### M4-08. План сетевых правил прокси (Core)
`macOS` · S · зависит от: M1-09, M4-01

**Сделать:** `TransparentProxyNetworkPlan`: включаемые правила (TCP и UDP к сетям `AllowedIPs` после исключения локальных) и исключаемые (loopback, link-local, multicast, адреса endpoint-ов).
**Тесты сначала:** `0.0.0.0/0` с исключением локальных сетей; несколько пиров; endpoint по доменному имени (исключается разрезолвленный адрес).
**Готово, когда:** план строится без NetworkExtension; маппинг в `NENetworkRule` — тонкий адаптер.

### M4-09. Определение приложения-источника
`macOS` · M · зависит от: M4-01, SP-2

**Сделать:** `SourceApplicationResolver`: `sourceAppSigningIdentifier` → быстрый путь; `sourceAppAuditToken` → `SecCodeCopyGuestWithAttributes` → Team ID и путь; LRU-кэш по `(pid, pidversion)`; поведение для случаев, найденных в SP-2 (WebKit, `nsurlsessiond`). Только публичные API (решение D-10).
**Тесты сначала:** логика кэша и выбора источника на фейковом `CodeIdentityReader`; разбор audit token из байтовой фикстуры.
**Готово, когда:** на каждый поток не больше одного обращения к Security-фреймворку на процесс.

### M4-10. Ретрансляция TCP и UDP (горячий путь)
`macOS` · L · зависит от: M4-06, M4-07

**Сделать:** `TCPFlowRelay`: `open`, два насоса, half-close, ошибки, таймауты. `UDPFlowRelay`: `readDatagrams` / `writeDatagrams`, ассоциации из `UDPAssociationTable`. Выделенные `DispatchQueue`, пул буферов, без лишних копий. Адресат ретрансляции задаётся параметром: это позволяет переиспользовать насосы в DNS-прокси (M4-13). Отступления от правил ради скорости описываются в документе фичи.
**Тесты сначала:** протоколы-обёртки над `NEAppProxyTCPFlow` и `NEAppProxyUDPFlow` позволяют тестировать насосы на фейковых потоках: порядок байтов, backpressure, закрытие с любой стороны, ошибка в середине передачи.
**Готово, когда:** тесты насосов проходят, ручная проверка: загрузка 1 ГБ и 4K-видео через выбранный браузер.

### M4-11. Сессия прозрачного прокси
`macOS` · L · зависит от: M4-08, M4-09, M4-10, M2-12

**Сделать:** `TransparentProxySession`: загрузка активного туннеля и секретов, компиляция `RoutingPolicySnapshot`, запуск `usernet` и его регистрация в общем для провайдеров `TunnelRuntimeRegistry` (actor), применение `NETransparentProxyNetworkSettings` по плану M4-08, обработка `handleNewFlow` и `handleNewUDPFlow` через `FlowRoutingDecider`, остановка, смена сети. Класс `TransparentProxyProvider` в `Apps/NetworkSystemExtension` только делегирует сессии. Запись в журнал подозрительной атрибуции (признак конфликта с другим прокси).
**Тесты сначала:** сессия на фейковых портах: порядок старта; поток выбранного приложения → туннель; невыбранного → `false`; остановка закрывает все ретрансляции и снимает регистрацию `usernet`.
**Готово, когда:** выбранный браузер ходит через туннель, остальные приложения — напрямую.

## DNSProxy

### M4-12. DNS-прокси: решения и ответы (Core)
`macOS` · M · зависит от: M4-01

**Сделать:** в фиче `DNSProxy` Core: `DNSQueryRouteDecider` поверх `ApplicationMatcher` и политики (источник запроса + готовность туннеля → `.throughTunnel` / `.toOriginalResolver` / `.refuse`), `DNSRefusalResponseBuilder` (тот же ID и вопрос, флаг QR, `RCODE = REFUSED`), `DNSUpstreamSelection` (DNS из конфига туннеля или запасной адрес через туннель).
**Тесты сначала:** таблица решений: выбранное и невыбранное приложение, туннель готов и не готов, `.block` и `.bypass`, неизвестный источник → исходный резолвер; построение `REFUSED` для фикстур запросов (A, AAAA, EDNS, несколько вопросов).
**Готово, когда:** вся логика DNS-прокси покрыта тестами без NetworkExtension.

### M4-13. Сессия DNS-прокси
`macOS` · L · зависит от: M4-10, M4-11, M4-12, SP-9

**Сделать:** `DNSProxySession` и класс `DNSProxyProvider` в `Apps/NetworkSystemExtension` (только делегирует): UDP- и TCP-потоки DNS. Запрос выбранного приложения уходит через `usernet` из `TunnelRuntimeRegistry` на DNS туннеля (насосы из M4-10). Запрос остальных приложений уходит к исходному адресату потока через обычный сокет. При `.refuse` возвращается ответ из `DNSRefusalResponseBuilder`. Любая внутренняя ошибка → пересылка исходному резолверу.
**Тесты сначала:** сессия на фейках: маршрутизация по решению; ошибка `usernet` → исходный резолвер; `usernet` не запущен → поведение по политике; TCP-запрос с префиксом длины.
**Готово, когда:** у выбранного `RoutingProbe` на DNS отвечает сервер туннеля, у невыбранного `dig` — системный резолвер; при сбое DNS-прокси система не теряет DNS.

## TunnelConnection и поведение

### M4-14. Слоты прокси и DNS-прокси, смена режима
`macOS` · M · зависит от: M2-10, M4-11, M4-13

**Сделать:** `TransparentProxySlotController` (`NETransparentProxyManager` + `NETunnelProviderProtocol`) и `DNSProxySlotController` (`NEDNSProxyManager`). `ActivateTunnelUseCase` в режиме выбора приложений включает оба слота и при отключении выключает оба. Смена режима активного туннеля = остановить одни слоты и запустить другие. Если DNS-прокси не включился, туннель всё равно работает, а пользователь видит предупреждение об утечке DNS-запросов.
**Тесты сначала:** сценарии на фейках: активация в каждом режиме; смена режима на активном туннеле; активация другого туннеля в другом режиме; сбой включения DNS-прокси → туннель активен + предупреждение; отключение выключает оба слота.
**Готово, когда:** переключение режимов не оставляет лишних активных слотов.

### M4-15. Изменение выбора на лету и блокировка при недоступности
`macOS` · M · зависит от: M2-07, M4-11, M4-13

**Сделать:** сообщение `applyRoutingPolicy` атомарно подменяет matcher и в transparent proxy, и в DNS-прокси; сигнал готовности туннеля (успешное рукопожатие и его свежесть) → вход `FlowRoutingDecider` и `DNSQueryRouteDecider`; `.block` закрывает поток с ошибкой «соединение отклонено». По умолчанию для новых туннелей — `.block` (решение D-06).
**Тесты сначала:** обработчик сообщения: новая политика действует для новых потоков и DNS-запросов; готовность меняется при устаревании рукопожатия (`FixedWallClock`); политика по умолчанию — `.block`.
**Готово, когда:** добавление приложения в выбор работает без переподключения; при остановленном сервере и `.block` выбранное приложение не выходит в сеть.

### M4-17. Тесты утечек на macOS
`macOS` · M · зависит от: M4-15

**Сделать:** `Scripts/RoutingProbe` — подписанная CLI-утилита: печатает внешний IP, результат DNS-запроса, ответивший резолвер и результат подключения. Скрипт `Scripts/leak-test-macos.sh`: выбранный `RoutingProbe` → IP сервера и DNS туннеля; невыбранный `curl` → IP провайдера и системный DNS; сервер остановлен + `.block` → у `RoutingProbe` ошибка и `REFUSED`; IPv6-адресат при туннеле без IPv6 → блокировка.
**Тесты сначала:** это и есть тесты; запускаются вручную перед каждым релизом (нужно одобренное системное расширение).
**Готово, когда:** все проверки зелёные на macOS 26 и 27.
