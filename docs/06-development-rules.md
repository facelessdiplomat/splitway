# 06. Правила разработки

Правила обязательны для всего кода проекта: Swift, Go, C-заголовков, скриптов и конфигураций сборки. Почти все проверяются автоматически (раздел 11). Если правило мешает, его меняют в этом документе, а не нарушают в коде.

## 1. Никаких комментариев в коде

**Абсолютно никаких.** Запрещены:
- `//` и `/* */` в Swift, Go, C, shell-скриптах, YAML;
- документирующие комментарии (`///`, `/** */`);
- `// MARK:`, `// TODO:`, `// FIXME:`;
- закомментированный код;
- заголовки с лицензией и авторством в файлах (лицензия лежит в `LICENSE` в корне);
- подавление линтера комментарием (`// swiftlint:disable`, `//nolint`).

Чем заменять комментарии:

| Хочется написать комментарий… | Вместо этого |
|---|---|
| объясняющий, что делает код | переименовать функцию или переменную, чтобы это было видно из имени |
| разделяющий части файла (`MARK`) | вынести части в расширения в отдельных файлах `Type+Capability.swift` |
| объясняющий магическое число | именованная константа или value object (`MTU.minimumForIPv6`) |
| объясняющий почему так сделано | раздел «Решения» в `docs/features/<Feature>.md` |
| описывающий контракт | тест, который этот контракт проверяет |
| TODO | задача в плане или в трекере |

Это **не** комментарии, а синтаксис инструментов, без которого код не работает (решение D-18):
- Go: `//go:build`, `//export`, `//go:linkname` и преамбула cgo перед `import "C"`;
- Swift: обязательная первая строка `// swift-tools-version:` в `Package.swift`;
- shell: строка интерпретатора `#!/usr/bin/env bash`;
- данные, а не код: тестовые фикстуры, которые имитируют пользовательский ввод (строки `#` в файлах wg-quick), и фикстуры самого линтера в `Scripts/LintFixtures`.

Сторонний код (если когда-то понадобится его вендорить) лежит в `ThirdParty/` без изменений, с исходными лицензиями, и исключён из линтинга.

## 2. Понятные и самоописывающие имена

- Следуем [Swift API Design Guidelines](https://www.swift.org/documentation/api-design-guidelines/) и идиомам Go.
- Имя говорит, **что** это и **зачем**, а не как устроено: `excludesPrivateNetworks`, а не `flag2`; `UniqueTunnelNameResolver`, а не `NameHelper`.
- Булевы значения читаются как утверждения: `isActive`, `hasHandshake`, `excludesPrivateNetworks`.
- Функции с побочными эффектами — глаголы (`activate`, `save`), без побочных — существительные или описания результата (`publicKey`, `routes(for:)`).
- Сокращения только общепринятые предметные: IP, DNS, MTU, TCP, UDP, CIDR, UAPI, NAT, QR. Регистр по правилам Swift: `IPAddress`, `ipAddress`, `dnsServers`.
- Запрещены безликие суффиксы: `Manager`, `Helper`, `Utils`, `Util`, `Misc`, `Common`, `Data` (как суффикс сущности), `Info`. Исключение — имена системных типов Apple, которые мы не выбираем (`NETunnelProviderManager`).
- Однобуквенные имена допустимы только для индексов в коротких циклах и для получателей методов в Go.
- Один основной тип на файл, имя файла = имя типа. Расширения — `Type+Capability.swift`.
- Тесты называются поведением: `rejectsPortAboveUpperBound`, `importsValidConfigsAndReportsInvalidOnes`.

## 3. ООП, SOLID и лучшие практики

### SOLID в этом проекте

| Принцип | Как применяем | Пример |
|---|---|---|
| S — единственная ответственность | У типа одна причина для изменения | Парсер, сериализатор и калькулятор `AllowedIPs` — три разных типа |
| O — открытость для расширения | Новое поведение — новый тип за протоколом, а не флаг в существующем | Новый источник импорта реализует `ImportSource`, остальной код не меняется |
| L — подстановка Барбары Лисков | Любая реализация порта соблюдает его контракт, включая фейки | Фейк репозитория не бросает ошибок, которых не бросает реальный |
| I — разделение интерфейсов | Порты маленькие и про одно | `TunnelSecretStore` не знает об именах и порядке туннелей |
| D — инверсия зависимостей | `Core` зависит от портов, `Infrastructure` реализует их, связывание — в composition root | `ActivateTunnelUseCase` получает `SystemTunnelController` через `init` |

### Практики Swift

- Доменные типы — `struct` и `enum`. Ссылочные типы — `final class` по умолчанию; `actor` для общего изменяемого состояния.
- Композиция вместо наследования. Наследование — только там, где его требует Apple (`NEPacketTunnelProvider`, `NETransparentProxyProvider`), и такие классы только делегируют работу.
- Иммутабельность по умолчанию (`let`), никакого глобального изменяемого состояния, никаких синглтонов в нашем коде.
- Зависимости передаются через `init`. Никаких service locator и глобальных контейнеров.
- Минимальный уровень доступа: `private` по умолчанию, `public` только для API модуля.
- Ошибки — типизированные (`throws(TunnelConfigurationError)`), со смыслом для домена. Запрещены `try!`, `as!`, force unwrap и `fatalError` в продакшен-коде. В тестах — `#require`.
- Swift 6 strict concurrency без `@unchecked Sendable` и `nonisolated(unsafe)`, кроме горячих путей с обоснованием (раздел 7). Модели представления — `@MainActor`. Никаких блокирующих вызовов на кооперативном пуле. Отмена задач поддерживается.
- `@preconcurrency import` допустим только в файле наследника класса Apple, когда система передаёт ему объект без аннотации `Sendable`, а владение объектом переходит к нам (потоки `NEAppProxyFlow` в `TransparentProxyProvider`). Файл только делегирует, объект сразу уходит в адаптер с настоящей синхронизацией, а причина описана в документе фичи.
- Только публичные API Apple, приватные API запрещены (решение D-10). Никаких SDK аналитики и автоматического сбора сбоев (решение D-22).
- Запрещены `print` и `NSLog`, только `Logger`. Прямой доступ к `UserDefaults.standard`, `FileManager.default` и системным синглтонам — только в `Infrastructure`.

### Практики Go

- `gofmt`, `go vet`, проверка комментариев (раздел 11). Пакеты делятся по фичам, а не по техническим слоям.
- Ошибки возвращаются и оборачиваются (`fmt.Errorf("…: %w", err)`), паника не пересекает границу cgo: каждая экспортируемая функция ловит её и возвращает код ошибки.
- Go-указатели не передаются в C: только хэндлы из таблицы. Все горутины имеют понятное время жизни и останавливаются при остановке туннеля.
- Тесты табличные, разборщики пакетов и DNS покрыты fuzz-тестами.

## 4. TDD и DDD

### TDD

Цикл: **красный → зелёный → рефакторинг**. Тест пишется до реализации и сначала падает.

**Покрываем тестами то, где есть логика:**
- доменные типы, инварианты, разбор и сериализация, алгоритмы (CIDR, сопоставление, решения по потоку, трансляция адресов);
- сценарии (use cases) с фейковыми портами;
- модели представления: маппинг состояния в отображение и реакции на действия;
- адаптеры инфраструктуры с собственной логикой (миграции, кодеки, построение правил);
- Go-пакеты.

**Не покрываем:** вёрстку SwiftUI, тонкие обёртки над системными API без логики, сгенерированный код, composition root.

Правила тестов:
- Swift Testing (`@Suite`, `@Test`, параметризованные тесты для таблиц кейсов).
- Фейки вместо моков: простые реализации портов в памяти в таргете `<Feature>TestSupport`. Без фреймворков мокирования.
- Тесты детерминированы: время через `WallClock`, никакой реальной сети в unit-тестах, никаких `sleep`.
- Структура «подготовка → действие → проверка» видна по пустым строкам, а не по комментариям.
- Один тест — одно поведение. Имя теста — это его документация.
- UI-тесты (`UITests/`) пишутся на XCTest и XCUITest: Swift Testing не умеет управлять приложением. Каждый UI-тест запускает приложение на английском, во временном хранилище (`-SplitwayUsesTemporaryStorage YES`) и с пройденным или непройденным онбордингом, а ключевые экраны проверяет аудитом доступности `performAccessibilityAudit`. Исключение — живой тест `LiveTunnelTests`: он работает только на устройстве с импортированным тестовым туннелем, с сохранёнными туннелями и включается переменной `SPLITWAY_LIVE_TUNNEL=YES` (`Scripts/live-tunnel-test.sh <устройство>`). На симуляторах он пропускается.

### DDD

- **Логика в модели, отображение отдельно.** Домен и сценарии лежат в `Core` и не знают о SwiftUI, NetworkExtension и файлах. Вью только показывает состояние модели и передаёт действия.
- Value objects валидируются при создании, после чего невалидного состояния не бывает.
- Агрегаты (`TunnelConfiguration`, `Tunnel`) сами следят за своими инвариантами.
- Границы контекстов = фичи. Фича пользуется другой только через публичные типы её `Core`.
- Единый язык (ubiquitous language): одни и те же слова в коде, документах и интерфейсе.

| Термин в документах | Тип в коде | Значение |
|---|---|---|
| Туннель | `Tunnel` | Сохранённый туннель пользователя: имя, конфигурация, политика |
| Конфигурация | `TunnelConfiguration` | Содержимое конфига WireGuard |
| Интерфейс / пир | `InterfaceConfiguration` / `PeerConfiguration` | Секции `[Interface]` и `[Peer]` |
| Политика маршрутизации | `RoutingPolicy` | Что идёт в туннель: всё, выбранные приложения или выбранные сервисы |
| Выбранные приложения | `ApplicationSelection` | Набор `ApplicationIdentity` (macOS) |
| Сервис | `ServiceProfile` | Набор доменов и подсетей из каталога или пользователя |
| Решение по потоку | `FlowRouteDecision` | `.tunnel`, `.direct`, `.block` |
| Слот | `SystemTunnelController` | Системная VPN-конфигурация, в которую записывается активный туннель |
| Движок | `TunnelEngine` | wireguard-go за C API |

## 5. Фичи и папки

- Код делится по фичам: у каждой фичи своя папка `Packages/SplitwayKit/Sources/Features/<Feature>/` со слоями `Core/{Domain,UseCases,Ports}`, `Infrastructure`, `Presentation` (подробно в [02-architecture.md](02-architecture.md), раздел 4).
- Тесты повторяют структуру: `Tests/Features/<Feature>/…`.
- Go-пакеты тоже по фичам: `fdtunnel`, `usernet`, `servicerouting`.
- Общий код попадает в `SharedKernel`, только если его используют минимум две фичи и он не содержит логики конкретной фичи.
- Новая фича создаётся, когда появляется новый контекст со своими терминами и правилами. Добавить экран к существующей фиче — не повод для новой фичи.

## 6. Никаких god objects

Признаки god object: много несвязанных зависимостей, «менеджер всего», методы для разных фич, файл, который правится в каждой задаче. Такой тип дробится на сценарии, политики и value objects.

Ориентиры (SwiftLint предупреждает, а `Scripts/check.sh` не даёт слить ветку при превышении жёстких порогов):

| Метрика | Мягкий порог | Жёсткий порог |
|---|---|---|
| Строк в теле типа | 200 | 300 |
| Строк в функции | 30 | 50 |
| Строк в файле | 300 | 400 |
| Параметров функции / зависимостей в `init` | 5 | 7 |
| Цикломатическая сложность | 8 | 12 |

Превышение жёсткого порога допустимо **только при крайней необходимости**, например в разборщике пакетов на горячем пути. Тогда есть обоснование в документе фичи, а для файла — исключение в `.swiftlint.yml` по пути (не комментарием в коде).

## 7. Оптимизация

- Об эффективности думаем с самого начала: правильные структуры данных, отсутствие O(n²) на растущих коллекциях, никакого I/O на главном потоке, ленивая загрузка иконок и тяжёлых данных.
- **Читаемость важнее мелких оптимизаций.** Мелкая оптимизация делается строго по правилам.
- Отступать от правил ради скорости можно только на **горячих путях** из [02-architecture.md](02-architecture.md), раздел 10: пакетный цикл в Go, ретрансляция потоков, решение по потоку, сопоставление доменов и подсетей. Допустимые отступления: unsafe-указатели и ручное управление буферами, конкретные типы вместо протоколов-экзистенциалов, `DispatchQueue` вместо Swift Concurrency, `@unchecked Sendable` с внутренней синхронизацией, функции длиннее порога.
- Каждое отступление: (1) подтверждено бенчмарком или профилем, (2) покрыто тестами, (3) описано в разделе «Спорные решения» документа фичи с цифрами «до» и «после».

## 8. Коммиты и авторство

- **ИИ-ассистент никогда не указывается автором или соавтором коммита.** Запрещены трейлеры `Co-Authored-By` с ИИ, строки «Generated with…» в сообщениях коммитов и описаниях pull request. Коммиты создаются от имени разработчика по его `git config`; ассистент не меняет `user.name` и `user.email`.
- Формат сообщения — Conventional Commits **на английском** (решение D-24), область = фича: `feat(TunnelConfiguration): parse multi-value AllowedIPs`. В теле — ID задачи (`Task: M1-07`).
- Ветка на задачу (решение D-26): `feature/<task-id>-<slug>`, `fix/<slug>`, `spike/SP-x`. Слияние в основную ветку `master` (решение D-31) — `git merge --no-ff` и только после успешного `Scripts/check.sh` (его запускает хук `pre-merge-commit`), затем `git push` в `origin`. CI нет (решение D-23); `master` всегда рабочий.
- Коммит, закрывающий задачу, отмечает её чекбокс в файле вехи (решение D-27).
- Коммиты небольшие и атомарные: тесты и реализация одного поведения.

## 9. Документ по завершении фичи

В конце разработки каждой фичи создаётся `docs/features/<Feature>.md` по [шаблону](features/_TEMPLATE.md): что делает фича, зависимости, принцип работы, ключевые решения и **спорные решения** (с альтернативами и причинами), отступления от правил, ограничения, что покрыто тестами. При значимом изменении фичи документ обновляется в той же ветке задачи.

## 10. Чек-лист ревью

- [ ] Нет комментариев (линтер зелёный).
- [ ] Имена понятны без контекста задачи.
- [ ] Логика в `Core`, вью без логики; `Core` не импортирует UI и системные фреймворки.
- [ ] Тесты написаны на поведение, детерминированы, без моков-фреймворков.
- [ ] Нет god objects, пороги размеров соблюдены.
- [ ] Горячий путь: есть бенчмарк и запись в документе фичи.
- [ ] Строки локализованы (`ru`, `en`), есть подписи доступности, аудит `Scripts/check.sh --ui` проходит.
- [ ] Секреты не попадают в журнал, `UserDefaults`, `providerConfiguration`.
- [ ] Документ фичи создан или обновлён, если фича завершена или изменилась.
- [ ] В коммитах нет ИИ-авторства.
- [ ] Чекбокс задачи отмечен в файле вехи.

| Правило | Инструмент | Где |

| Нет комментариев в Go | `Scripts/go-comment-check` (`go/ast`, директивы разрешены) | хук `pre-commit`, `Scripts/check.sh` |
