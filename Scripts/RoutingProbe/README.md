# RoutingProbe и тесты утечек на macOS

Ручная проверка режима «Только выбранные приложения» перед каждым релизом (задача M4-17). Нужен Mac с одобренным системным расширением Splitway: настоящий Mac или тестовая ВМ (решение D-32).

## Что проверяется

`Scripts/leak-test-macos.sh <сценарий>` сравнивает выбранную в туннеле утилиту RoutingProbe с невыбранными `curl` и `dig` и печатает `PASS`, `FAIL` или `SKIP` для каждой проверки.

| Сценарий | Проверки |
|---|---|
| `selected` | Выбранный RoutingProbe выходит в интернет через туннель, а `curl` — напрямую. На DNS-запрос RoutingProbe к системному резолверу отвечает резолвер туннеля, а на запрос `dig` — системный. IPv6 выбранного RoutingProbe на туннеле без IPv6 отклоняется сразу. С `TUNNEL_CARRIES_IPV6=yes` скрипт ждёт, что IPv6 пройдёт через туннель, а в сети без IPv6 проверку пропускает |
| `unavailable` | При неотвечающем сервере и включённой блокировке выбранный RoutingProbe не выходит в интернет и получает отказ сразу, а не по тайм-ауту. Его DNS-запрос получает `REFUSED`, а `curl` продолжает работать: для этой проверки он открывает `captive.apple.com`, имя, которое RoutingProbe не спрашивает. Строка `INFO` показывает, резолвит ли `curl` имя `api.ipify.org`, на которое RoutingProbe получил отказ. Обычно нет: `mDNSResponder` около минуты отдаёт этот отказ всем приложениям ([DNSProxy](../../docs/features/DNSProxy.md)) |
| `background` | Фоновая загрузка (`nsurlsessiond`), которую выбранный RoutingProbe поставил с задержкой 5 с и сразу завершился, доходит до сервера. Строка `INFO` показывает, куда она ушла. На macOS 26 — напрямую: после выхода приложения `nsurlsessiond` отправляет загрузку от своего имени, и прокси не может отнести её к приложению (M4-19). Если строка покажет туннель, поведение системы изменилось |

Адреса скрипт не печатает: они видны с `--show-addresses`.

## RoutingProbe

Утилита подписана сертификатом Apple Development команды `8625S77CSU`, identifier — `com.facelessdiplomat.splitway.routing-probe`. Она лежит в бандле `RoutingProbe.app`: так её можно выбрать в листе приложений как обычное приложение. При запуске она печатает три строки:

```
address ok <внешний адрес> 412ms
resolver ok NOERROR <адрес резолвера> 35ms
ipv6 failed refused 2ms
```

- `address` — HTTPS-запрос к `api.ipify.org`.
- `resolver` — DNS-запрос без кэша `mDNSResponder` к первому `nameserver` из `/etc/resolv.conf` за `whoami.akamai.net`: ответ — внешний адрес резолвера, который спросил Akamai.
- `ipv6` — TCP-подключение к `[2606:4700:4700::1111]:443`.

Разбор DNS покрыт тестами (`swift test --package-path Scripts/RoutingProbe`, шаг `Scripts/check.sh`).

## Режимы замеров

Для замеров скорости и задержки (задача M4-16) у RoutingProbe есть ещё три режима:

| Команда | Что делает | Что печатает |
|---|---|---|
| `RoutingProbe download <адрес> [попытки]` | загружает адрес, по умолчанию 3 раза | на попытку `bytes`, `seconds`, `mbps`, `status`, `first-byte-ms`, в конце медиану `mbps` |
| `RoutingProbe upload <адрес> [попытки] [байты]` | отправляет POST с телом из нулей, по умолчанию 3 раза по 25 МБ | то же, что загрузка |
| `RoutingProbe latency <адрес> [попытки]` | открывает новое соединение на каждую попытку, по умолчанию 10 раз | фазы `dns-ms`, `tcp-ms`, `tls-ms`, `first-byte-ms` и протокол, в конце медианы фаз |
| `RoutingProbe background-start <адрес> [задержка]` | ставит фоновую загрузку в сессию `URLSession` с идентификатором `<bundle ID>.background`, которая начнётся через заданное число секунд (по умолчанию 5), и завершается | `background started` с номером задачи |
| `RoutingProbe background-collect [тайм-аут]` | подключается к той же фоновой сессии и ждёт результат загрузки, по умолчанию до 30 с | `background ok <тело ответа>` или `background failed <причина>` |

Каждая попытка идёт в новой эфемерной сессии `URLSession`: соединения и кэши между попытками не переиспользуются. Время фаз берётся из `URLSessionTaskTransactionMetrics`. У HTTP/3 фаза `tcp-ms` почти нулевая: подключение по QUIC входит в `tls-ms`. При неверных аргументах RoutingProbe печатает подсказку и завершается с кодом 2.

## Как запустить

```bash
Scripts/build-routing-probe.sh
cp -R build/RoutingProbe/RoutingProbe.app /Applications/
```

1. В Splitway: туннель без IPv6 в режиме «Только выбранные приложения», в выборе — только RoutingProbe. Подключить туннель.
2. `Scripts/leak-test-macos.sh selected`
3. Туннель, сервер которого не отвечает: сервер остановлен или в конфиге неотвечающий endpoint, например `192.0.2.1:51820`. В выборе — RoutingProbe, «Блокировать трафик, если туннель недоступен» включено. Подключить и подождать 20 с: первые 15 с туннель считается готовым, а готовность проверяется раз в 5 с.
4. `Scripts/leak-test-macos.sh unavailable`

В тестовой ВМ `Scripts/macos-vm.sh leak-test <сценарий>` собирает RoutingProbe, ставит её в `/Applications` ВМ и запускает скрипт там. Туннель в ВМ готовится так же, через приложение.

## Замеры ретрансляции

`Scripts/relay-benchmark-macos.sh <метка>` меряет текущий режим Mac и печатает строки `ключ=значение`:

| Строка | Что в ней |
|---|---|
| `idle` | CPU расширения за 20 с без трафика |
| `route` | совпадает ли внешний адрес RoutingProbe с адресом `curl` |
| `latency` | медианы фаз 10 подключений |
| `dns` | медиана времени ответа резолвера системы на 5 запросов мимо кэша |
| `single-stream` | медиана скорости 3 загрузок, CPU-секунды расширения на гигабайт, загрузка системы в ядрах, неудачные попытки |
| `parallel-streams` | то же для двух загрузок одновременно |
| `packets` | пакеты физических интерфейсов `en*` за одну загрузку: сколько исходящих на один входящий |

Адрес загрузки и адрес задержки меняются переменными `RELAY_BENCHMARK_DOWNLOAD` и `RELAY_BENCHMARK_LATENCY`. По умолчанию это `proof.ovh.net`: он отдаёт 100 МиБ и разрешает две загрузки с одного адреса одновременно. `speed.cloudflare.com` после нескольких десятков загрузок отвечает 429; такие попытки скрипт не считает в скорости и показывает в `failed-attempts`.

Режимы сравниваются прогонами подряд, потому что скорость пути меняется от прогона к прогону: «Весь трафик», «Только выбранные приложения» с выбранным RoutingProbe, снова «Весь трафик» и так далее. Цель для режима прокси — в [SP-3](../../docs/features/spikes/SP-3.md). В тестовой ВМ — `Scripts/macos-vm.sh relay-benchmark <метка>`.

## Ограничения

- `curl` и `dig` не должны быть выбраны в туннеле: они дают адреса для сравнения.
- В сети без IPv6 (например, в ВМ) проверка IPv6 пропускается.
- После сценария `unavailable` имя `api.ipify.org` около минуты не резолвится ни у одного приложения. Сценарии `selected` и `background` запускаются через минуту или после сброса кэша: `sudo dscacheutil -flushcache; sudo killall -HUP mDNSResponder`.
- Проверка `selected` сравнивает только адреса. Если резолвер туннеля и системный резолвер выходят в интернет с одного адреса, она даст ложный `FAIL`.
- Скрипт полагается на `api.ipify.org` и `whoami.akamai.net`.
