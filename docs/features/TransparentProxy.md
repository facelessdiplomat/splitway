## Назначение

Прозрачный прокси режима «Только выбранные приложения». Фича решает, какие потоки система отдаёт провайдеру, определяет их приложение и ретранслирует их через `usernet`. Пока готовы план сетевых правил (какие адресаты система передаёт провайдеру, а какие всегда идут мимо него) и политики ретрансляции, по которым будут работать насосы M4-10.

## Принцип работы

### План сетевых правил

`TransparentProxyNetworkPlan(for:resolvedEndpointAddresses:)` строится из конфигурации туннеля и адресов, которые получились при резолвинге endpoint-ов:

- **Включаемые сети** (`includedNetworks`):
  - объединение `AllowedIPs` всех пиров через `IPNetworkSet`, перекрытия сливаются;
  - «исключить локальные сети» уже учтено в самих `AllowedIPs`;
  - туннель, который забирает весь публичный IPv4, но не весь глобальный IPv6, дополнительно получает `2000::/3` (`IPv6LeakProtection.applying(to:)`, решение D-30). Такие потоки выбранных приложений доходят до `FlowRoutingDecider`, и без IPv6 в туннеле он их блокирует.

  Эти же сети сессия передаёт в `RoutingPolicySnapshot.tunnelNetworks`.
- **Исключаемые сети** (`excludedNetworks`):
  - loopback, link-local и multicast обоих семейств;
  - адреса endpoint-ов: литералы из конфигурации и адреса, которые сессия получила при резолвинге (включая синтезированные NAT64).

  В `NETransparentProxyNetworkSettings` у исключающих правил приоритет. Без них собственный UDP-трафик движка мог бы снова попасть в перехват.

Оба набора действуют для TCP и UDP. Адаптер сессии (M4-11) превращает каждую сеть из `networks` в `NENetworkRule` с протоколом `.any`.

### Политики ретрансляции

- `RelayPolicy.standard` собирает две политики. Свои значения проверяются при создании (`RelayPolicyError`), а стандартные заданы константами.

  | Политика | Поле | Стандартное значение |
  |---|---|---|
  | `TCPRelayPolicy` | `chunkByteCount` — блок насоса | 64 КиБ |
  | | `connectTimeout` — подключение через туннель | 30 с |
  | | `idleTimeout` — простой в обе стороны | 2 ч 4 мин |
  | `UDPRelayPolicy` | `datagramBufferByteCount` — приём датаграммы | 65 535 байт, самая большая датаграмма |
  | | `idleTimeout` — простой ассоциации | 5 мин |
  | | `maximumAssociations` — адресатов на один поток | 256 |

- `UDPAssociationTable<Destination, Association>` — ассоциации одного UDP-потока, по одной на адресата. Время приходит параметром (`at:`), поэтому таблица детерминирована.
  - `insert` возвращает ассоциацию, которая покинула таблицу: прежнюю ассоциацию того же адресата или, если таблица полна, ту, что дольше всех без активности. Её закрывает насос.
  - `recordActivity` отмечает датаграмму в любую сторону.
  - `removeExpired(at:)` забирает ассоциации, которые простаивали `idleTimeout` или дольше.
  - `remove` и `removeAll` нужны при сбое одной ассоциации и при закрытии потока.

  Поиск и отметка активности — O(1). Линейный проход нужен только для вытеснения и периодической очистки.
- `HostnameResolutionPolicy` решает, куда подключаться (`RelayTarget`):
  - по имени из `remoteHostname`, которое `usernet` резолвит через DNS туннеля;
  - или по адресу, который выбрала система.

  Адрес остаётся, если:
  - туннель не может резолвить имена;
  - имени нет или это не доменное имя (литералы IPv4 и IPv6, мусор);
  - имя из mDNS (`.local`, RFC 6762): его нельзя отправлять обычному DNS.

  Из разрезолвленных адресов `address(choosingFrom:insteadOf:)` берёт первый того же семейства, что и у системы, и внутри сетей туннеля. Если такого нет, остаётся адрес системы: решение `FlowRoutingDecider` принято именно по нему.

## Публичный API

`TransparentProxyNetworkPlan`, `RelayPolicy`, `TCPRelayPolicy`, `UDPRelayPolicy`, `RelayPolicyError`, `UDPAssociationTable`, `HostnameResolutionPolicy`, `RelayTarget`.

## Решения

- Включаемые сети — только `AllowedIPs`, без подсетей адресов интерфейса: пакет к адресу, который не принимает ни один пир, wireguard-go всё равно отбросит.
- Исключаемые сети не вычитаются из включаемых. У исключающих правил и так приоритет, а вычитание адреса endpoint-а из `0.0.0.0/0` дало бы десятки лишних правил.
- Литералы endpoint-ов план берёт из конфигурации сам, а разрезолвленные адреса передаёт сессия. Литерал исключается, даже если резолвинг для него не выполнялся.
- Правило D-30 общее с пакетным туннелем: `IPv6LeakProtection.applying(to:)` из `PacketTunnel`.
- Простой TCP — 2 ч 4 мин, как минимальный тайм-аут установленного соединения для NAT (RFC 5382). Простой UDP-ассоциации — 5 мин, как рекомендует RFC 4787. Соединения, которые живут за домашним роутером, переживут и прокси.
- Таблица ассоциаций обобщена по типу адресата и ассоциации: насос M4-10 сам выберет ключ (например, `NWEndpoint`) и хэндл `usernet`, а Core не знает о NetworkExtension.
- Таймауты — `Duration`, время активности — `Date`. Простой считается как `Duration.seconds(moment.timeIntervalSince(lastActivity))`.

## Спорные решения

| Решение | Альтернативы | Почему так | Когда пересмотреть |
|---|---|---|---|
| `2000::/3` во включаемых сетях туннеля только с IPv4, как в D-30 для режима «Весь трафик» | Только `AllowedIPs`: IPv6 выбранных приложений идёт напрямую | Иначе выбранное приложение на двухстековой сети выходит в интернет по IPv6 мимо туннеля и раскрывает адрес. Невыбранные приложения провайдер отпускает решением `.direct`, это почти бесплатно | Если IPv6-потоки невыбранных приложений заметно нагрузят провайдер |
| Адрес endpoint-а исключается целиком, для всех портов и протоколов | Исключать только UDP на порт endpoint-а | Правило по сети проще, а самому VPN-серверу выбранное приложение почти никогда не пишет | Если понадобится ходить к серверу VPN через туннель |
| Полная таблица вытесняет ассоциацию, которая дольше всех без активности | Отклонять датаграммы к новым адресатам | Приложение с одним сокетом на много адресатов (DHT, игры) продолжает работать; вытесненная ассоциация обычно уже не нужна | Если вытеснение начнёт рвать живые обмены |
| Разрезолвленный адрес берётся только того же семейства, что у системы | Любой адрес внутри туннеля | Система уже выбрала семейство (Happy Eyeballs, блокировка IPv6), а решение по потоку принято для её адреса | Нет |
| Имя из `remoteHostname` резолвится через туннель повторно | Всегда подключаться к адресу системы | Если запрос DNS ушёл мимо туннеля (DNS-прокси не включился или не узнал приложение), CDN выдаёт адрес для реального местоположения пользователя. Цена — запрос DNS через туннель при новом подключении | Если задержка подключения в M4-16 окажется заметной: тогда резолвить только при неактивном DNS-прокси |

## Ограничения и известные проблемы

- Правила применяются вместе с сессией прокси (M4-11). Проверить план в системе можно только с одобренным системным расширением, то есть с подписью.
- Туннель с IPv6-адресом, но только с частью IPv6-сетей (без `::/0`): поток выбранного приложения к глобальному IPv6 уходит в туннель, и wireguard-go его отбрасывает. Соединение ждёт тайм-аута, как и в режиме «Весь трафик».
- Стандартные значения политик подбираются по замерам M4-16.

## Тесты

25 тестов в `TransparentProxyTests`:

- план сетевых правил (7):
  - `0.0.0.0/0` с исключением локальных сетей: включаются только публичные сети IPv4;
  - туннель только с IPv4 получает `2000::/3`, у двухстекового остаются оба маршрута по умолчанию;
  - объединение `AllowedIPs` нескольких пиров;
  - исключение loopback, link-local и multicast;
  - исключение адресов endpoint-ов: литералов IPv4 и IPv6 и разрезолвленных адресов имени.
- политики (7): стандартные тайм-ауты не короче, чем у домашних роутеров, буфер вмещает самую большую датаграмму, свои значения в пределах, отказ для пустого блока, буфера вне размеров датаграммы, неположительных тайм-аутов и лимита меньше одного;
- таблица ассоциаций (6): поиск, истечение по простою, продление активностью, вытеснение самой давней при заполнении, замена без вытеснения, удаление одной и всех;
- выбор имени или адреса (5): имя через туннель; адрес для пустого имени, литералов, `.local` и мусора; адрес без DNS в туннеле; выбор разрезолвленного адреса того же семейства внутри туннеля; адрес системы, если подходящих нет.
