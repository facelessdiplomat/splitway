# DNSProxy

| | |
|---|---|
| Статус | готово: ответ REFUSED, выбор DNS-сервера и адреса из ответов; ими пользуется прозрачный прокси, своего провайдера нет (решение D-34) |
| Платформы | macOS |
| Задачи | M4-12, M4-13, M4-16, M4-18 |
| Таргеты | `DNSProxy` |

## Назначение

Логика DNS режима «Только выбранные приложения» (решения D-09 и D-34). Фича выбирает DNS-сервер, который несёт туннель, и строит ответ `REFUSED`. Ими пользуется прозрачный прокси (`TransparentProxy`): запрос выбранного приложения он отправляет на этот сервер, а заблокированный запрос получает отказ. Отдельного `NEDNSProxyProvider` нет: по SP-9 он видит те же приложения, а при падении оставляет систему без DNS.

## Принцип работы

### Откуда приходят запросы

[SP-9](spikes/SP-9.md) записывал каждый поток DNS, который видел `NEDNSProxyProvider`, в том числе вместе с прозрачным прокси в режиме «Только выбранные приложения» (тестовая ВМ macOS 26.6):

| Источник запроса | `sourceAppSigningIdentifier` | Процесс по audit token | `remoteHostname` |
|---|---|---|---|
| Safari | `com.apple.Safari` | сам Safari | запрашиваемое имя |
| Службы Safari | `com.apple.Safari.SafeBrowsing`, `com.apple.Safari.SearchHelper` | сами службы | есть |
| Приложение с `WKWebView` или на CFNetwork | identifier приложения | само приложение | есть |
| `curl`, `ssh`, `dscacheutil` | свои identifier | сами процессы | есть |
| `dig` со своим резолвером (по SP-2 так же Chrome и Electron) | свой identifier | сам процесс | нет |
| Собственные запросы `mDNSResponder` | `com.apple.mDNSResponder` | `mDNSResponder` | есть |
| `nsurlsessiond` | `com.apple.nsurlsessiond` | код не читается | есть |
| Системные службы (`helpd`, `parsecd`, `softwareupdated` и другие) | свои identifier | сами службы | есть |

Что из этого следует:

- DNS-прокси видит те же приложения, что и прозрачный прокси, и ничего сверх. Запрос, который `mDNSResponder` отправляет за приложение, приходит в прозрачный прокси UDP-потоком этого приложения к порту 53 раньше, чем в DNS-прокси. Поэтому запросы выбранных приложений обрабатывает прозрачный прокси, и своего провайдера у фичи нет (решение D-34).
- Без атрибуции остаются собственные запросы `mDNSResponder` и запросы к link-local резолверу: их не отнести к приложению ни в одном провайдере, и они идут напрямую.
- Падение DNS-прокси в SP-9 оставляло всю систему без DNS примерно на минуту — ещё одна причина решения D-34.

### Ответ REFUSED

`DNSRefusalResponseBuilder.response(refusing:)` строит ответ на запрос в формате DNS (без двухбайтового префикса длины TCP: его снимает и добавляет сессия):

- тот же ID, тот же код операции и все вопросы запроса байт в байт, в том числе со сжатыми именами;
- флаги QR, RD и CD из запроса, `RCODE = REFUSED`; AA, TC, RA и AD сброшены;
- разделы ответов и полномочий пусты;
- если в запросе была запись OPT (EDNS), в ответе тоже есть OPT (RFC 6891). В ней размер UDP 1232 байта, флаг DO из запроса (RFC 3225) и нет опций клиента, например cookie.

Разбор (`DNSQueryLayout`, `DNSMessageReader`) только находит конец раздела вопросов и запись OPT. Указатели сжатия пропускаются, а не разыменовываются, поэтому петли из указателей разбору не страшны. Ошибки — `DNSMessageError`:

| Ошибка | Когда |
|---|---|
| `truncatedHeader` | сообщение короче заголовка |
| `notAQuery` | это ответ (стоит QR) |
| `malformedQuestion` | вопрос обрезан или имя неверно |
| `malformedRecord` | обрезана или неверна запись после вопросов |

На неразборчивый запрос прозрачный прокси не отвечает (`DNSRefusalRelay`).

`DNSAddressAnswers(parsing:)` читает ответ: имя единственного вопроса (в нижнем регистре, как `DomainName`) и записи A и AAAA класса IN из раздела ответов вместе с их временем жизни (`DNSAddressRecord`). Записи CNAME и другие пропускаются, адреса за ними засчитываются имени вопроса. Ответ с ошибкой (RCODE не 0) даёт пустой список. Имя читает `DNSMessageReader.readName()`: он идёт по указателям сжатия только назад, поэтому петля из указателей невозможна. Кроме ошибок из таблицы бывает `notAResponse` — это запрос, а не ответ. Ответами пользуется `TunnelAnsweredNames` прозрачного прокси.

### DNS-сервер в туннеле

`DNSUpstreamSelection(for:fallbackServer:)` выбирает серверы, которые туннель действительно несёт:

- адрес внутри `AllowedIPs` пиров;
- у интерфейса есть адрес того же семейства.

Порядок выбора:

1. Серверы из конфига туннеля, которые туннель несёт, в исходном порядке.
2. Если таких нет — запасной сервер через туннель: `1.1.1.1` по умолчанию.
3. Если туннель не несёт и его — `nil`, и запросы выбранных приложений идут к исходному резолверу без перенаправления.

Защита D-30 (`2000::/3`) сюда не входит: эти адреса туннель не несёт, а блокирует.

## Публичный API

`DNSRefusalResponseBuilder`, `DNSAddressAnswers`, `DNSAddressRecord`, `DNSMessageError`, `DNSUpstreamSelection`. Для тестов других фич — `DNSResponseFixture` в `DNSProxyTestSupport`.

## Решения

- Без DNS-сервера в туннеле запросы выбранного приложения уходят к исходному резолверу: так делает и пакетный туннель с конфигом без DNS. Блокировка при недоступном туннеле всё равно отвечает отказом.
- Решение для запроса DNS принимает `FlowRoutingDecider` прозрачного прокси по адресату после перенаправления, поэтому своего решающего типа у фичи нет: `DNSQueryRouteDecider` удалён вместе с DNS-прокси (решение D-34).
- Размер UDP в OPT ответа — 1232 байта, рекомендация DNS Flag Day 2020: ответ не фрагментируется.
- Сообщения — `[UInt8]`, а не `Data`: индексы начинаются с нуля, и у срезов нет ловушек со смещёнными индексами. Сессия переводит `Data` из потока один раз.
- Запасной сервер настраивается при сборке зависимостей (`fallbackServer`), значение по умолчанию задаёт фича.

## Спорные решения

| Решение | Альтернативы | Почему так | Когда пересмотреть |
|---|---|---|---|
| Флаг RA в отказе сброшен | Ставить RA, как у рекурсивного резолвера | Отказ означает, что рекурсия для этого клиента не выполняется | Если клиент поведёт себя иначе на отказ без RA |
| Опции клиента в OPT ответа не повторяются | Отражать cookie (RFC 7873) | Сервер без поддержки cookie их просто не возвращает, клиент это допускает | Нет |

## Ограничения и известные проблемы

- Версия EDNS запроса не проверяется: на версию выше 0 приходит REFUSED, а не BADVERS.
- Запросы к link-local резолверу и собственные запросы `mDNSResponder` не перенаправляются ([03](../03-platform-macos.md), раздел 6.5).
- Отказ, полученный выбранным приложением через системный резолвер, `mDNSResponder` кэширует для всех приложений. Ответ `REFUSED` он считает отказом сервера: штрафует резолвер на 60 с и около 77 с отвечает на это имя отрицательно любому процессу. Невыбранное приложение всё это время не может разрезолвить имя, которое выбранное приложение спрашивало при недоступном туннеле. Другие имена работают. В ВМ так же долго держатся `SERVFAIL`, пустой ответ, NXDOMAIN и пустой ответ с SOA и TTL 0. Положительная заглушка с TTL 0 держится около 7 с, но даёт невыбранным приложениям ненастоящий адрес. Настоящий ответ можно получить только мимо туннеля, то есть с утечкой имени, поэтому отказ остаётся (M4-17, 2026-10-31).

## Тесты

24 теста в `DNSProxyTests`:

- ответ REFUSED (9):
  - фикстуры запросов A с рекурсией, AAAA без рекурсии, EDNS с cookie и флагом DO и без него, два вопроса со сжатым именем;
  - ошибки: короткий заголовок, ответ вместо запроса, обрезанный вопрос, объявленная, но отсутствующая запись;
  - 20 000 обрезанных и испорченных запросов от `SeededRandomNumberGenerator`: разбор не падает, а ответ всегда несёт ID запроса.
- выбор DNS-сервера (6): серверы конфига внутри туннеля, пропуск серверов вне `AllowedIPs` и семейства без адреса, запасной `1.1.1.1` и свой запасной, нет сервера для туннеля с частью сетей.
- адреса из ответа (9): A и AAAA с временем жизни, адреса за CNAME, имя в нижнем регистре, ошибки резолвера, запрос вместо ответа, короткий заголовок, обрезанная запись, указатель на себя, несколько вопросов.

Запуск: `swift test --package-path Packages/SplitwayKit --filter DNSProxy`.
