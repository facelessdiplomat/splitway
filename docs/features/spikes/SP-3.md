# SP-3. Скорость ретрансляции через netstack

| | |
|---|---|
| Статус | закрыт: замерено в тестовой ВМ macOS 26.6 (M0-12) 2026-10-31, цель M4-16 записана. По решению D-36 замеры делаются в ВМ; повторный замер вечером 2026-10-31, в том числе отправки, — в [TransparentProxy](../TransparentProxy.md), раздел «Производительность» |
| Вопрос | Насколько режим «Только выбранные приложения» (прозрачный прокси → `usernet` на gVisor netstack → WireGuard) уступает режиму «Весь трафик» (пакетный туннель) по скорости, задержке и CPU; какую цель поставить M4-16 |
| Код | ветка `spike/SP-3`: режимы `download`, `upload` и `latency` в RoutingProbe и скрипты замеров `Scripts/relay-performance`; в `master` не сливается |
| Вывод | **Ретрансляция через netstack годится для v1.** Прокси не упирается ни в окно, ни в процессор: при скорости пути 110–200 Мбит/с он даёт 70–90 % скорости «Весь трафик» одним потоком и 90–105 % двумя. Цена — в 1,3–1,5 раза больше CPU на гигабайт и лишний круг до сервера туннеля на каждое TCP-подключение. Код Swift занимает меньше 2 % профиля; основную добавку дают подтверждения TCP из netstack, их в 3,5–4,5 раза больше, чем у TCP системы |

## Как мерили

- ВМ macOS 26.6, 4 vCPU, на Mac разработчика (решение D-32). Сеть ВМ идёт через NAT хоста с MTU 1280 ([README ВМ](../../../Scripts/macos-vm/README.md)). Туннель — конфиг коммерческого провайдера (Прага, решение D-29) без строки `MTU`.
- Сборки приложения: Debug, как ставит `Scripts/macos-vm.sh install`, и Debug с оптимизацией Swift (`-O`, whole module). Release не проверялся: его подпись требует профиля Developer ID. Ядро Go в обеих сборках одинаковое.
- Режимы шли подряд: напрямую (туннель выключен), «Весь трафик», «Только выбранные приложения» с одним выбранным RoutingProbe. Адрес RoutingProbe отличался от адреса невыбранного `curl` только в последнем режиме.
- Замеры RoutingProbe — `URLSession`, новая эфемерная сессия на каждую попытку:
  - задержка — 10 подключений, медианы фаз DNS, TCP, TLS и первого байта из `URLSessionTaskTransactionMetrics`;
  - DNS — 5 запросов мимо кэша к резолверу системы (`whoami.akamai.net`), в режиме прокси запрос уходит на DNS туннеля (решение D-34);
  - загрузка — одним потоком 3 × 100 МиБ с `proof.ovh.net` и 5 × 50 МБ с `speed.cloudflare.com`, затем несколько потоков параллельно;
  - отправка — 3 × 10–25 МБ на `speed.cloudflare.com/__up`.
- CPU — CPU-секунды процесса расширения (`ps -o cputime`) за время загрузок в пересчёте на гигабайт, загрузка системы по `top`, простой — 20 с без трафика.
- Профиль — `sample` процесса расширения 6 с посреди загрузки 100 МиБ, собственное время функций по частям.
- Пакеты — счётчики `en0` за загрузку 100 МиБ.
- iperf3 не использовался: своего сервера нет (решение D-29).

## Результаты

### Задержка и DNS

Медианы в миллисекундах, диапазон — по прогонам:

| | Напрямую | «Весь трафик» | Выбранные приложения |
|---|---|---|---|
| TCP-подключение | 71–72 | 72–83 | 145–152 |
| TLS | 109–143 | 107–127 | 108–140 |
| Первый байт | 104–128 | 95–121 | 100–127 |
| Ответ DNS резолвера системы | 2 | 72–84 | 72–83 |

TLS зависит от сервера: у Cloudflare — около 110 мс во всех режимах, у OVH — 122–143 мс.

- TCP-подключение через прокси дольше на один круг до сервера туннеля (63–78 мс). Перед подключением прокси резолвит `remoteHostname` потока через DNS туннеля (`ProxiedFlowRouter.tunnelAddress`), и кэша у этого резолвинга нет. HTTP/3 этого круга не платит: UDP-поток резолвинга не делает, и у `one.one.one.one` по HTTP/3 подключение заняло 1–5 мс, а рукопожатие — один круг, 93–104 мс.
- Ответ DNS через прокси не медленнее, чем в режиме «Весь трафик»: в обоих режимах запрос идёт на DNS туннеля. Первый запрос нового имени — 120–255 мс.

### Скорость загрузки

Мбит/с:

| Сервер и потоки | Напрямую | «Весь трафик» | Выбранные приложения |
|---|---|---|---|
| OVH, один поток, медиана | 120 | 133–150 | 110–122 |
| OVH, два потока, сумма | 237 | 185–215 | 195 |
| Cloudflare, один поток, медиана | 149–154 | 132–172 | 115–120 |
| Cloudflare, четыре потока, сумма | 274 | 294–330 | — |

- Скорость пути меняется от прогона к прогону на 20–30 %, поэтому режимы сравнивались прогонами подряд. Один поток через прокси — 70–90 % от «Весь трафик», два потока — 90–105 %.
- Окно gVisor скорость не ограничивает. В этой версии gVisor буфер приёма подстраивается до 4 МиБ: `moderateReceiveBuffer` включён по умолчанию, а `gonet` вызывает `ModerateRecvBuf` при каждом чтении. Один поток с OVH через прокси шёл 147 Мбит/с при круге 77–83 мс, а окно 1 МиБ пропустило бы не больше 109 Мбит/с.
- Больше 200–300 Мбит/с путь ВМ не пропускает, поэтому потолок самого прокси не найден. Бенчмарк `usernet` (M4-05) на Apple M4 Pro — 760 Мбит/с.
- Четыре потока через прокси с Cloudflare не замерены: после нескольких десятков загрузок Cloudflare стал отвечать 429. OVH разрешает только две параллельные загрузки с одного адреса.
- Отправка во всех режимах шла 4–53 Мбит/с с разбросом в разы, в том числе напрямую: её ограничивает путь, и режимы в ВМ не сравнить. Из шести отправок через прокси одна оборвалась ошибкой «The network connection was lost», в других режимах из двенадцати не оборвалась ни одна.

### CPU

| | «Весь трафик» | Выбранные приложения |
|---|---|---|
| CPU расширения на гигабайт загрузки | 31–36 с | 44–49 с |
| Расширение, один поток | 51–65 % ядра | 61–69 % ядра |
| Расширение, два потока OVH | 76–88 % ядра | 116 % ядра |
| Система, один поток | 0,8–1,2 ядра | 1,0–1,3 ядра |
| Система, два потока OVH | 1,4–1,6 ядра | 1,9 ядра |
| Простой без трафика | 0 % | 0 % |

- На гигабайт прокси тратит в 1,3–1,5 раза больше CPU, чем пакетный туннель.
- Сборка с оптимизацией Swift тратит столько же, сколько Debug: 44,1 и 44,2 с на гигабайт при той же скорости и задержке.

### Профиль

Доля собственного времени функций среди занятых выборок `sample`. Ожидания (`__psynch_cvwait`, `__workq_kernreturn`, `kevent` и подобные) не считаются. В режиме «Весь трафик» не считается и `read` из `utun`: этот поток почти всё время ждёт пакетов.

| Часть | «Весь трафик» | Выбранные приложения |
|---|---|---|
| Отправка UDP-пакетов WireGuard (`sendmsg` из Go) | 14 % (173) | 32 % (922) |
| Приём UDP-пакетов (`recvmsg`) | 32 % (403) | 17 % (496) |
| Запись в `utun` | 10 % (130) | — |
| Пробуждение потоков Go (`psynch_cvsignal`) | 11 % (142) | 4 % (109) |
| Рантайм Go | 14 % (173) | 14 % (397) |
| gVisor netstack | — | 7 % (198) |
| Шифрование WireGuard | 7 % (94) | 5 % (144) |
| wireguard-go | 7 % (91) | 3 % (94) |
| Запуск потоков GCD (`start_wqthread`) | — | 6 % (178) |
| Часы (`mach_absolute_time`, почти всё из Go) | 3 % (36) | 4 % (100) |
| Запись в поток NetworkExtension (`flow_director_ctl_write`) | — | 3 % (76) |
| Код Swift и Foundation | 0,3 % (4) | 1,5 % (42) |
| Всего занятых выборок | 1273 | 2847 |

Главная добавка прокси — отправка пакетов WireGuard: в 5,3 раза больше выборок при сопоставимой скорости загрузки (122 и 128–138 Мбит/с). Дальше идут gVisor, рантайм Go и потоки GCD.

### Пакеты

За загрузку 100 МиБ:

| | «Весь трафик» | Выбранные приложения |
|---|---|---|
| Входящих пакетов `en0` | 99–104 тыс. | 77 тыс. |
| Исходящих пакетов `en0` | 13,5–14,2 тыс. | 37–47 тыс. |
| Исходящих на один входящий | 0,14 | 0,48–0,61 |
| Средний входящий пакет | 1230–1260 байт | около 1485 байт |

- Исходящие пакеты при загрузке — почти все подтверждения TCP. TCP системы подтверждает примерно каждый седьмой сегмент, а gVisor — примерно каждый второй. Каждое подтверждение — отдельное шифрование и отдельный `sendmsg`: на macOS wireguard-go отправляет пакеты по одному. Отсюда большая часть лишнего CPU.
- Размер пакетов разный из-за MTU. Без MTU в конфиге пакетный туннель берёт MTU пути минус 80 байт (`TunnelMTU.pathMTUWithOverhead`), в ВМ это 1200. `usernet` всегда получает 1420 (`TransparentProxyStarter.standardWireGuardMTU`). На пути с MTU 1280 пакеты WireGuard прокси получаются по 1500 байт: исходящие система фрагментирует, а входящие в ВМ доходили. В сети, которая теряет большие пакеты, прокси может зависать там, где пакетный туннель работает.

## Вывод

- Ретрансляция через netstack годится для v1. Переносить насосы в Go или увеличивать буферы ради скорости не нужно: код Swift — меньше 2 % профиля, а окно gVisor подстраивается само.
- Цена режима:
  - в 1,3–1,5 раза больше CPU на гигабайт, в основном из-за подтверждений TCP из gVisor;
  - лишний круг до сервера туннеля на каждое TCP-подключение из-за повторного резолвинга имени;
  - MTU `usernet` не учитывает путь.
- Один поток через прокси на 10–30 % медленнее, чем в режиме «Весь трафик». В ВМ причину не найти: разница сравнима с разбросом пути.

## Цель для M4-16

Сравнение с режимом «Весь трафик» на том же Mac и с тем же сервером, медиана трёх чередующихся прогонов:

| Метрика | Сейчас, ВМ | Цель |
|---|---|---|
| Скорость одного TCP-потока | 70–90 % | не меньше 90 % |
| Скорость нескольких потоков | 90–105 % | не меньше 95 % |
| CPU расширения на гигабайт | 1,3–1,5 × | не больше 1,25 × |
| TCP-подключение к имени, уже разрезолвленному через туннель | +63–78 мс, один круг | не больше +10 мс |
| Ответ DNS через прокси | вровень | не больше +5 мс |
| Отправка | в ВМ не сравнить | не меньше 90 %, замер на Mac |
| CPU расширения в простое | 0 % | 0 % |

Что пробовать, по убыванию пользы:

1. Не резолвить имя повторно, если адрес уже пришёл с DNS туннеля. После D-34 запросы выбранных приложений и так перенаправляются на DNS туннеля, и прокси видит ответы. Можно запоминать их по имени с учётом TTL, а резолвить через туннель только адреса, полученные мимо него, например из кэша `mDNSResponder`.
2. Меньше подтверждений TCP из netstack: GRO на сетевом интерфейсе gVisor или другое объединение входящих сегментов. `netstack.CreateNetTUN` из wireguard-go прячет стек gVisor, так что понадобится своя сборка стека в `usernet`. Лицензия wireguard-go — MIT, атрибуция уже обязательна (решение D-14).
3. MTU `usernet` по пути, как у пакетного туннеля: MTU пути минус 80 байт.
4. Меньше пробуждений на блок данных: переходы между очередями GCD в ретрансляции и таймеры Go и gVisor.

Методика и скрипты — в ветке `spike/SP-3`, папка `Scripts/relay-performance`. M4-16 переносит режимы замеров RoutingProbe в `master` вместе с тестами.

Итог M4-16 (2026-10-31): в ВМ все цели, которые там можно проверить, достигнуты — первые три рычага из списка. Таблица «до и после» — в [TransparentProxy](../TransparentProxy.md), раздел «Производительность».

## Попутные находки

- **После обновления расширение недоступно до перезагрузки.** При замене расширения новой сборкой `launchd` не отдал новому заданию Mach-сервис `8625S77CSU.com.facelessdiplomat.splitway.network-extension`: «The endpoint … already exists and is owned by» старым заданием. Старое задание `launchd` удалил в ту же миллисекунду, но уже после. Приложение получало `extensionUnreachable` (`bootstrap look-up: No such process`), и туннели не включались до перезагрузки ВМ. Первая замена в той же загрузке ВМ прошла: тогда старое задание удалилось раньше, чем пришло новое. Это гонка в системе. SP-9 видел её с включённым DNS-прокси, а теперь она случилась без него. Обновление через Sparkle (M7) могло оставить пользователя без туннелей до перезагрузки. Исправлено 2026-10-31: в имени Mach-сервиса номер сборки, и новое задание не сталкивается со старым ([SecretDelivery](../SecretDelivery.md)).
- **Второе окно при открытии конфига.** Если Splitway уже открыт, открытие файла `.conf` (двойной щелчок в Finder, `open`) создаёт второе главное окно, и лист импорта показывается в обоих окнах. Лист редактора туннеля после этого тоже открывался в обоих. Исправлено 2026-10-31: открытый файл получает уже открытое окно ([TunnelImport](../TunnelImport.md)).
- Тестовые серверы Hetzner и Linode через выходной сервер туннеля не открываются и в режиме «Весь трафик»: обрыв соединения и ошибка TLS. Поэтому замеры шли с OVH и Cloudflare.

## Ограничения

- ВМ с 4 vCPU и сетью через NAT хоста: абсолютные цифры ориентировочные. M4-16 повторяет замеры на Mac владельца, там же — первая проверка цели.
- Путь ВМ не пропускает больше 200–300 Мбит/с: потолок прокси не найден.
- Отправку в ВМ не сравнить: разброс пути больше разницы режимов.
- Память расширения не замерялась.
- `sample` делает примерно одну выборку на поток в 1,5 мс, и число выборок пропорционально времени CPU лишь приблизительно. Поэтому расход CPU в выводах взят из `ps`, а профиль показывает только доли.
