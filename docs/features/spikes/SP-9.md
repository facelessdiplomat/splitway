# SP-9. Атрибуция DNS-запросов в DNS-прокси

| | |
|---|---|
| Статус | проверен в тестовой ВМ macOS 26.6 (M0-12) 2026-10-30; владелец выбрал вариант A (решение D-34); подтверждение на Mac владельца — позже |
| Вопрос | Что видит `NEDNSProxyProvider` в метаданных DNS-потока; работают ли провайдеры в одном процессе; что происходит с DNS системы при падении и остановке DNS-прокси ([03-platform-macos.md](../../03-platform-macos.md), раздел 6.5). После SP-2 добавился вопрос: нужен ли DNS-прокси, если запросы приложений и так приходят в прозрачный прокси |
| Код | ветка `spike/SP-9` (поверх `spike/SP-2`), в `master` не сливается |
| Вывод | DNS-прокси видит те же приложения, что и прозрачный прокси, и ничего сверх. Запросы выбранных приложений прозрачный прокси забирает раньше. Зато DNS-прокси добавляет риски для DNS всей системы. **Предложение — не использовать `NEDNSProxyProvider` в v1** (вариант A ниже) |

## Как проверяли

- В том же системном расширении — `DNSProxyProvider` из ветки спайка:
  - пишет в журнал каждый DNS-поток через `FlowAttributionProbe` из SP-2 вместе с pid процесса провайдера;
  - пересылает UDP-запросы исходному резолверу через `NWConnection`;
  - DNS-потоки TCP только записывает и закрывает: они редки и для вопроса спайка не нужны.
- Приложение с `-SplitwayDNSProxySpikeEnable` и `-SplitwayDNSProxySpikeDisable` сохраняет конфигурацию `NEDNSProxyManager` с identifier расширения. Отдельного разрешения сохранение не потребовало: VPN-конфигурации в ВМ уже были разрешены.
- Случаи:
  - только DNS-прокси;
  - DNS-прокси вместе с прозрачным прокси в режиме «Только выбранные приложения» (выбраны Safari и апплет на CFNetwork), в обоих порядках включения;
  - `kill -9` процесса расширения;
  - выключение конфигурации.
- Источники запросов:
  - Safari, апплеты на CFNetwork и на `WKWebView`;
  - `curl`, `ssh`, `dscacheutil`;
  - `dig` со своим резолвером, как у Chrome и Electron в SP-2.

  Кэш DNS сбрасывался перед каждым шагом.

## Результаты

| Источник запроса | `sourceAppSigningIdentifier` | Процесс по audit token | `remoteHostname` |
|---|---|---|---|
| Safari | `com.apple.Safari` | сам Safari | запрашиваемое имя |
| Службы Safari | `com.apple.Safari.SafeBrowsing`, `com.apple.Safari.SearchHelper` | сами службы | есть |
| Апплет с `WKWebView` | identifier апплета | сам апплет | есть |
| Апплет на CFNetwork | identifier апплета | сам апплет | есть |
| `curl`, `ssh`, `dscacheutil` | свои identifier | сами процессы | есть |
| `dig` (свой резолвер) | `com.apple.dig` | сам `dig` | нет |
| Собственные запросы `mDNSResponder` | `com.apple.mDNSResponder` | `mDNSResponder` | есть |
| `nsurlsessiond` | `com.apple.nsurlsessiond` | код не читается | есть |
| Системные службы (`helpd`, `parsecd`, `softwareupdated`, `translationd` и другие) | свои identifier | сами службы | есть |

Chrome, Firefox и VS Code в этот раз не запускались. По SP-2 Firefox резолвит имена системным резолвером, как `curl`, а Chrome и VS Code — своим, как `dig`.

Ещё наблюдения:

- **Один процесс.** Оба провайдера обрабатывали потоки в одном процессе расширения: pid 801 до перезагрузки и 937 после. Общий `usernet` в процессе возможен, но провайдеры создаёт система. Чтобы их связать, нужен объект на весь процесс, а это противоречит запрету синглтонов (раздел 3 правил).
- **Порядок перехвата.** Когда работают оба провайдера, DNS-запрос приложения сначала приходит в прозрачный прокси. Если тот отвечает `false` (приложение не выбрано), запрос доходит до DNS-прокси. Запросы выбранных приложений прозрачный прокси забирает сам и отправляет на DNS туннеля, до DNS-прокси они не доходят.
- **Падение.** Система перезапустила процесс расширения через 0,1 с после `kill -9`, а `dig` к резолверу снова работал через 10 с. Запросы через системный резолвер (`curl`) не проходили 50–60 с, потом всё заработало. Пока DNS-прокси включён, его падение оставляет всю систему без DNS примерно на минуту.
- **Остановка.** Выключение конфигурации останавливает провайдер («Configuration was disabled»), и следующий же запрос проходит.
- **Обновление расширения при включённом DNS-прокси.** После установки новой сборки система сразу перезапустила DNS-прокси на новой версии. Приложение при этом перестало находить Mach-сервис расширения (`bootstrap look-up: No such process`): доставка секретов не проходила, и туннели не включались до перезагрузки ВМ. Не проверено, бывает ли так при работающем прозрачном прокси или пакетном туннеле.
- **Не воспроизвелось.** В первом прогоне с обоими провайдерами запросы невыбранных приложений не проходили около двух минут. После перезагрузки оба порядка включения работали. Причина не выяснена.

## Вывод

- DNS-прокси видит те же приложения, что и прозрачный прокси, и ничего сверх.
- Запросы выбранных приложений прозрачный прокси получает раньше и уже отправляет через туннель (M4-11).
- Без DNS-прокси остаются непокрытыми два случая:
  - запросы к link-local резолверу — они входят в исключения правил прокси;
  - собственные запросы `mDNSResponder`. Их не отнести к приложению ни в одном из провайдеров.
- DNS-прокси добавляет риски:
  - падение оставляет всю систему без DNS примерно на минуту;
  - общий `usernet` требует объекта на весь процесс;
  - после обновления расширения приложение теряло связь с ним до перезагрузки.

## Предложение

Владелец выбрал вариант A (решение D-34, 2026-10-30). Оно меняет ADR-11 и задачи M4-13 и M4-14. Решение D-09 остаётся прежним: запросы выбранных приложений идут через туннель.

- **A (рекомендую).** Не использовать `NEDNSProxyProvider` в v1. DNS выбранных приложений обрабатывает прозрачный прокси, это уже сделано в M4-11. При недоступном туннеле и `.block` прокси отвечает на запрос `REFUSED` (`DNSRefusalResponseBuilder` из M4-12), а не закрывает поток. M4-13 сокращается до этого ответа и тестов утечек DNS, а M4-14 — до слота прокси, который уже готов. Нужны новая запись в журнале решений и правка ADR-11 и раздела 6.5.
- **B.** Оставить DNS-прокси, как в плане. Тогда M4-13 решает общий `usernet` (исключение из запрета синглтонов), разбор падений и обновлений расширения, а M4-14 — слот DNS-прокси.
