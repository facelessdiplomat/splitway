## Назначение

Прозрачный прокси режима «Только выбранные приложения». Фича решает, какие потоки система отдаёт провайдеру, определяет их приложение и ретранслирует их через `usernet`. Готовы план сетевых правил (какие адресаты система передаёт провайдеру, а какие всегда идут мимо него), политики и насосы ретрансляции TCP и UDP и определение приложения-источника потока. Сессию, которая связывает их с провайдером, добавит M4-11.

## Принцип работы

### План сетевых правил

`TransparentProxyNetworkPlan(for:resolvedEndpointAddresses:)` строится из конфигурации туннеля и адресов, которые получились при резолвинге endpoint-ов:

- **Включаемые сети** (`includedNetworks`):
  - объединение `AllowedIPs` всех пиров через `IPNetworkSet`, перекрытия сливаются;
  - «исключить локальные сети» уже учтено в самих `AllowedIPs`;
  - туннель, который забирает весь публичный IPv4, но не весь глобальный IPv6, дополнительно получает `2000::/3` (`IPv6LeakProtection.applying(to:)`, решение D-30). Такие потоки выбранных приложений доходят до `FlowRoutingDecider`, и без IPv6 в туннеле он их блокирует.

  Эти же сети сессия передаёт в `RoutingPolicySnapshot.tunnelNetworks`.
- **Исключаемые сети** (`excludedNetworks`):
  - loopback, link-local и multicast обоих семейств;
  - адреса endpoint-ов: литералы из конфигурации и адреса, которые сессия получила при резолвинге (включая синтезированные NAT64).

  В `NETransparentProxyNetworkSettings` у исключающих правил приоритет. Без них собственный UDP-трафик движка мог бы снова попасть в перехват.

Оба набора действуют для TCP и UDP. Адаптер сессии (M4-11) превращает каждую сеть из `networks` в `NENetworkRule` с протоколом `.any`.

### Политики ретрансляции

- `RelayPolicy.standard` собирает две политики. Свои значения проверяются при создании (`RelayPolicyError`), а стандартные заданы константами.

  | Политика | Поле | Стандартное значение |
  |---|---|---|
  | `TCPRelayPolicy` | `chunkByteCount` — блок насоса | 64 КиБ |
  | | `connectTimeout` — подключение через туннель | 30 с |
  | | `idleTimeout` — простой в обе стороны | 2 ч 4 мин |
  | `UDPRelayPolicy` | `datagramBufferByteCount` — приём датаграммы | 65 535 байт, самая большая датаграмма |
  | | `idleTimeout` — простой ассоциации | 5 мин |
  | | `maximumAssociations` — адресатов на один поток | 256 |

- `UDPAssociationTable<Destination, Association>` — ассоциации одного UDP-потока, по одной на адресата. Время приходит параметром (`at:`), поэтому таблица детерминирована.
  - `insert` возвращает ассоциацию, которая покинула таблицу: прежнюю ассоциацию того же адресата или, если таблица полна, ту, что дольше всех без активности. Её закрывает насос.
  - `recordActivity` отмечает датаграмму в любую сторону.
  - `removeExpired(at:)` забирает ассоциации, которые простаивали `idleTimeout` или дольше.
  - `remove` и `removeAll` нужны при сбое одной ассоциации и при закрытии потока.

  Поиск и отметка активности — O(1). Линейный проход нужен только для вытеснения и периодической очистки.
- `HostnameResolutionPolicy` решает, куда подключаться (`RelayTarget`):
  - по имени из `remoteHostname`, которое `usernet` резолвит через DNS туннеля;
  - или по адресу, который выбрала система.

  Адрес остаётся, если:
  - туннель не может резолвить имена;
  - имени нет или это не доменное имя (литералы IPv4 и IPv6, мусор);
  - имя из mDNS (`.local`, RFC 6762): его нельзя отправлять обычному DNS.

  Из разрезолвленных адресов `address(choosingFrom:insteadOf:)` берёт первый того же семейства, что и у системы, и внутри сетей туннеля. Если такого нет, остаётся адрес системы: решение `FlowRoutingDecider` принято именно по нему.

### Приложение-источник

`SourceApplicationResolver.sourceApplication(of:)` превращает audit token потока (`sourceAppAuditToken` из метаданных) в `SourceApplication`, по которому решает `FlowRoutingDecider`:

1. `AuditToken` разбирает 32 байта `audit_token_t`: восемь 32-битных слов в порядке байтов Mac (little-endian), слово 5 — pid, слово 7 — pidversion. Пара `ProcessInstance(identifier:version:)` отличает новый процесс с тем же pid.
2. Кэш LRU на 512 процессов (`LeastRecentlyUsedCache`) хранит готовый `SourceApplication` по `ProcessInstance`. Повторный поток того же процесса не трогает Security.
3. При промахе порт `CodeIdentityReader` читает `CodeIdentity`: signing identifier, Team ID, путь исполняемого файла и подпись Apple.
4. Signing identifier попадает в источник, только если его можно проверить: есть Team ID или код подписан Apple. Identifier ad-hoc кода выбран самим автором, поэтому такой процесс узнаётся только по пути. Так ad-hoc программа с identifier `com.apple.curl` не выдаст себя за выбранный `curl`.
5. Без audit token, а также если код процесса не читается, источник неизвестен (все поля пусты): поток идёт напрямую. Неудача тоже кэшируется.

Адаптер macOS `SecurityCodeIdentityReader` (`TransparentProxyInfrastructure`):

- `SecCodeCopyGuestWithAttributes` с `kSecGuestAttributeAudit` находит код процесса;
- `SecCodeCopySigningInformation` даёт identifier, Team ID и путь исполняемого файла (`kSecCodeInfoMainExecutable`, без символических ссылок);
- `SecCodeCheckValidity` с требованием `anchor apple` проверяет подпись Apple по коду в памяти, без хэширования файла.

Пропавший процесс — `processUnavailable`, нечитаемая подпись — `unreadableCode`.

### Ретрансляция

Насосы работают с портами `ProxiedStreamFlow` и `ProxiedDatagramFlow` (поток системы) и `UserspaceConnection` (соединение `usernet`). Адресата задаёт вызывающий, поэтому те же насосы пригодны для DNS-прокси (M4-13). У каждой ретрансляции своя последовательная очередь поверх общей целевой (`RelayEnvironment.targetQueue`); на ней идут подключение и блокирующая запись в `usernet`.

**`TCPFlowRelay`** (состояние — `TCPRelayProgress` за `Mutex`):

1. Подключение через туннель с `connectTimeout`. Если оно не удалось, поток системы закрывается без открытия: отказ → `refused`, тайм-аут → `timedOut`, остальное → `aborted`. Приложение видит неудачный `connect`.
2. После `open` два насоса:
   - **приложение → туннель**: следующий `read` потока только после того, как `usernet` принял предыдущий блок. Блок пишется из `Data` без копирования (`withUnsafeBytes`);
   - **туннель → приложение**: соединение читает блоками по `chunkByteCount` с окном в `windowChunkCount` (4) блока. Каждый принятый блок копируется в `Data` один раз и пишется в поток, а кредит возвращается, только когда поток принял запись.
3. Half-close: конец потока приложения закрывает запись соединения. Конец потока туннеля закрывает запись потока, но только после всех ожидающих записей. Когда закрыты обе стороны, соединение закрывается целиком, а поток — на чтение.
4. Ошибка туннеля посреди передачи сбрасывает поток (`peerReset` в обе стороны), ошибка потока закрывает соединение. `cancel()` прерывает обе стороны с `aborted`.
5. `closeIfIdle(at:)` закрывает ретрансляцию, простоявшую `idleTimeout`, с `timedOut`. Активностью считается блок в любую сторону.

**`UDPFlowRelay`**:

- каждая датаграмма уходит по ассоциации своего адресата в `UDPAssociationTable`; новая ассоциация — `openUDP` к адресату, которого вернул `destination` (nil — датаграмма отбрасывается). Вытесненная ассоциация закрывается;
- ответы пишутся в поток от исходного адресата, даже если `destination` отправил датаграмму в другое место (DNS-прокси); кредит возвращается после записи в поток, окно — `windowDatagramCount` (4) датаграммы;
- ошибка записи в ассоциацию удаляет её, следующая датаграмма откроет новую;
- `closeIfIdle(at:)` закрывает простоявшие ассоциации, а если не осталось ни одной и поток простоял `idleTimeout`, закрывает и поток;
- пустое чтение (приложение закрыло сокет) или ошибка потока закрывает все ассоциации.

Адаптеры macOS (`TransparentProxyInfrastructure`): `AppProxyStreamFlow` и `AppProxyDatagramFlow` оборачивают `NEAppProxyTCPFlow` и `NEAppProxyUDPFlow` (API macOS 15: `open(withLocalFlowEndpoint:)`, `readDatagrams` с `NWEndpoint`). `FlowEndpoint(_ endpoint: NWEndpoint)` и `networkEndpoint` переводят адреса через байты `IPAddress`, имена хостов не поддерживаются. `ProxiedFlowError(appProxyError:)` и `appProxyError` переводят ошибки в `NEAppProxyFlowError` и обратно.

## Решения

- Включаемые сети — только `AllowedIPs`, без подсетей адресов интерфейса: пакет к адресу, который не принимает ни один пир, wireguard-go всё равно отбросит.
- Исключаемые сети не вычитаются из включаемых. У исключающих правил и так приоритет, а вычитание адреса endpoint-а из `0.0.0.0/0` дало бы десятки лишних правил.
- Литералы endpoint-ов план берёт из конфигурации сам, а разрезолвленные адреса передаёт сессия. Литерал исключается, даже если резолвинг для него не выполнялся.
- Правило D-30 общее с пакетным туннелем: `IPv6LeakProtection.applying(to:)` из `PacketTunnel`.
- Простой TCP — 2 ч 4 мин, как минимальный тайм-аут установленного соединения для NAT (RFC 5382). Простой UDP-ассоциации — 5 мин, как рекомендует RFC 4787. Соединения, которые живут за домашним роутером, переживут и прокси.
- Таблица ассоциаций обобщена по типу адресата и ассоциации: насос M4-10 сам выберет ключ (например, `NWEndpoint`) и хэндл `usernet`, а Core не знает о NetworkExtension.
- Таймауты — `Duration`, время активности — `Date`. Простой считается как `Duration.seconds(moment.timeIntervalSince(lastActivity))`.
- `SourceApplicationResolver` синхронный: `handleNewFlow` должен вернуть ответ сразу, поэтому кэш защищён `Mutex`, а не actor.
- Обратные вызовы туннеля (`receive`, `finish`) обрабатываются синхронно под `Mutex`, без перехода на очередь: после вызова состояние насоса уже обновлено, и запись в поток начинается сразу.
- Классы потоков NetworkExtension не `Sendable`, поэтому адаптер держит поток за `Mutex`. Это настоящая синхронизация без `@unchecked Sendable`, а вызовы NE не блокируют: они только ставят работу в очередь системы.

## Спорные решения

| Решение | Альтернативы | Почему так | Когда пересмотреть |
|---|---|---|---|
| `2000::/3` во включаемых сетях туннеля только с IPv4, как в D-30 для режима «Весь трафик» | Только `AllowedIPs`: IPv6 выбранных приложений идёт напрямую | Иначе выбранное приложение на двухстековой сети выходит в интернет по IPv6 мимо туннеля и раскрывает адрес. Невыбранные приложения провайдер отпускает решением `.direct`, это почти бесплатно | Если IPv6-потоки невыбранных приложений заметно нагрузят провайдер |
| Адрес endpoint-а исключается целиком, для всех портов и протоколов | Исключать только UDP на порт endpoint-а | Правило по сети проще, а самому VPN-серверу выбранное приложение почти никогда не пишет | Если понадобится ходить к серверу VPN через туннель |
| Полная таблица вытесняет ассоциацию, которая дольше всех без активности | Отклонять датаграммы к новым адресатам | Приложение с одним сокетом на много адресатов (DHT, игры) продолжает работать; вытесненная ассоциация обычно уже не нужна | Если вытеснение начнёт рвать живые обмены |
| Разрезолвленный адрес берётся только того же семейства, что у системы | Любой адрес внутри туннеля | Система уже выбрала семейство (Happy Eyeballs, блокировка IPv6), а решение по потоку принято для её адреса | Нет |
| Код читается для каждого нового процесса, в том числе невыбранного | Не читать код, если signing identifier из метаданных не входит в выбор | У каждого выбранного приложения есть правило по пути: без пути не узнать исполняемый файл внутри бандла без собственного identifier. Чтение одно на процесс, а процессов с сетью немного | Если чтение подписи заметно в профиле M4-16 |
| Код процесса читается под блокировкой кэша | Читать вне блокировки и сохранять результат после | Ровно одно обращение к Security на процесс даже при параллельных потоках; ждут только потоки новых процессов | Если ожидание блокировки заметно в профиле M4-16 |
| Запись в `usernet` блокирует очередь своей ретрансляции | Неблокирующая запись с обратным вызовом из Go | Обратное давление получается само: следующий блок читается из потока, только когда `usernet` принял предыдущий. Блокируется очередь одной ретрансляции, а не общая | Если много одновременно заторможенных отправок займут слишком много потоков (профиль M4-16) |
| Окно туннель → приложение — 4 блока (256 КиБ) | Размер окна в `TCPRelayPolicy` | Пока нет замеров, хватает константы; насос не держит больше окна в памяти | Замеры M4-16 |
| Простой проверяет общий обход `closeIfIdle(at:)` из сессии | Таймер на каждую ретрансляцию | Один таймер на все потоки дешевле тысяч таймеров, а время приходит параметром и тесты детерминированы | Нет |
| Конец приёма UDP-ассоциации ничего не делает | Удалять ассоциацию по сигналу `finish` | Ассоциация не отличима от новой с тем же адресатом; сломанную ассоциацию удалит ошибка записи или простой | Если ICMP-ошибки начнут задерживать восстановление |
| Имя из `remoteHostname` резолвится через туннель повторно | Всегда подключаться к адресу системы | Если запрос DNS ушёл мимо туннеля (DNS-прокси не включился или не узнал приложение), CDN выдаёт адрес для реального местоположения пользователя. Цена — запрос DNS через туннель при новом подключении | Если задержка подключения в M4-16 окажется заметной: тогда резолвить только при неактивном DNS-прокси |

## Отступления от правил разработки

- Насосы на `DispatchQueue`, а не на Swift Concurrency (горячий путь, раздел 7 правил). Запись в `usernet` и подключение блокируют поток, и на кооперативном пуле они недопустимы. Варианта на Swift Concurrency для сравнения нет, поэтому цифр «до» и «после» тоже нет: базовую линию снимет M4-16 (`Scripts/check.sh --bench`).

## Ограничения и известные проблемы

- Правила применяются вместе с сессией прокси (M4-11). Проверить план в системе можно только с одобренным системным расширением, то есть с подписью.
- Туннель с IPv6-адресом, но только с частью IPv6-сетей (без `::/0`): поток выбранного приложения к глобальному IPv6 уходит в туннель, и wireguard-go его отбрасывает. Соединение ждёт тайм-аута, как и в режиме «Весь трафик».
- Стандартные значения политик подбираются по замерам M4-16.
- Поведение для потоков WebKit и `nsurlsessiond` уточнит спайк SP-2: чей audit token приходит в метаданных — процесса-посредника или приложения, от имени которого он работает.
- Signing identifier из метаданных (`sourceAppSigningIdentifier`) пока не используется: identifier берётся из подписи процесса.
- Насосы проверены на фейках. Загрузку 1 ГБ и 4K-видео через выбранный браузер можно проверить только с подписанным системным расширением.
- UDP-адресат с именем хоста вместо адреса отбрасывается: прокси получает такие датаграммы редко.

## Тесты

55 тестов в `TransparentProxyTests`:

- план сетевых правил (7):
  - `0.0.0.0/0` с исключением локальных сетей: включаются только публичные сети IPv4;
  - туннель только с IPv4 получает `2000::/3`, у двухстекового остаются оба маршрута по умолчанию;
  - объединение `AllowedIPs` нескольких пиров;
  - исключение loopback, link-local и multicast;
  - исключение адресов endpoint-ов: литералов IPv4 и IPv6 и разрезолвленных адресов имени.
- политики (7): стандартные тайм-ауты не короче, чем у домашних роутеров, буфер вмещает самую большую датаграмму, свои значения в пределах, отказ для пустого блока, буфера вне размеров датаграммы, неположительных тайм-аутов и лимита меньше одного;
- таблица ассоциаций (6): поиск, истечение по простою, продление активностью, вытеснение самой давней при заполнении, замена без вытеснения, удаление одной и всех;
- выбор имени или адреса (5): имя через туннель; адрес для пустого имени, литералов, `.local` и мусора; адрес без DNS в туннеле; выбор разрезолвленного адреса того же семейства внутри туннеля; адрес системы, если подходящих нет;
- audit token (2): pid и pidversion из байтовой фикстуры, отказ для другого размера;
- приложение-источник (8): Developer ID с Team ID и путём, код Apple без Team ID, отброшенный identifier ad-hoc кода, одно чтение на процесс, новое чтение для повторного pid, поток без audit token, запомненная неудача, вытеснение самого давнего процесса;
- `TCPFlowRelay` (12): порядок байтов в обе стороны, кредит только после записи в поток, окно и размер блока, half-close с обеих сторон и закрытие записи потока после ожидающих записей, конец обеих сторон, ошибка туннеля и потока посреди передачи, отказ, тайм-аут и остановленная сеть при подключении, простой, отмена;
- `UDPFlowRelay` (8): датаграммы к своим адресатам и ответы обратно, повторное использование ассоциации, маршрут вызывающего с ответом от исходного адресата, датаграмма без маршрута, вытеснение при заполнении, простой ассоциаций и потока, закрытие потока приложением, кредит после записи ответа.

Насосы проверяются на фейках `ScriptedStreamFlow`, `ScriptedDatagramFlow` и `InMemoryUserspaceNetwork` с `AwaitableState`: тест дожидается нужного состояния, без задержек и опроса. Прогон повторён 40 раз без сбоев.

7 тестов в `TransparentProxyInfrastructureTests` (только macOS): identifier и путь процесса тестов по его собственному audit token (`task_info` с `TASK_AUDIT_TOKEN`), `processUnavailable` для несуществующего процесса; адреса IPv4 и IPv6 из `NWEndpoint` и обратно, отказ для имени и URL; ошибки `NEAppProxyFlowError` в обе стороны.
