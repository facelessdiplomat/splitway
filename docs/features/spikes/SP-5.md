# SP-5. Секреты в системном расширении

| | |
|---|---|
| Статус | проверен в тестовой ВМ macOS 26.6 (M0-12) 2026-10-30, рабочая сборка после перезагрузки — 2026-10-31; поведение с включённым SIP — на Mac владельца (решение D-36) |
| Вопрос | Как передать конфигурацию с приватным ключом системному расширению, которое работает от root и не видит Keychain пользователя ([03-platform-macos.md](../../03-platform-macos.md), раздел 5) |
| Код | ветка `spike/SP-5`, в `master` не сливается |
| Вывод | **Вариант B: XPC через `NEMachServiceName` расширения и System Keychain** (решение D-33) |

## Как проверяли

Прототип в ветке `spike/SP-5`. Приложение, запущенное с `-SplitwaySecretsSpike`, создаёт случайную строку (UUID) вместо настоящего ключа и передаёт её тремя способами. Обе стороны пишут в журнал только первые 4 байта SHA-256 строки.

- **A.** Элемент в Keychain пользователя (data protection keychain и группа `…splitway.shared`, как у `KeychainTunnelSecretStore`), его persistent reference — в `passwordReference` слота, чтение — в `startTunnel` провайдера.
- **B.** `NSXPCListener` на `NEMachServiceName` расширения с `setConnectionCodeSigningRequirement` из `ClientCodeRequirement` (фича `SecretDelivery`), запись и чтение через `SecItem` с `kSecUseDataProtectionKeychain = false`.
- **C.** Строка в `providerConfiguration` слота, чтение — в `startTunnel` провайдера.

С `-SplitwaySecretsSpikeLoadOnly` приложение только читает элемент варианта B: так проверялись обновление расширения и перезагрузка.

ВМ: macOS 26.6.2, сборка разработки, расширение и VPN-конфигурация одобрены. SIP в образе выключен (особенность образа Cirrus Labs).

## Результаты

| Проверка | Результат |
|---|---|
| Процесс расширения | `uid 0`, песочница включена |
| A. Чтение `passwordReference` в провайдере | `-25291` (`errSecNotAvailable`, «No keychain is available»): у root-расширения нет Keychain пользователя |
| B. Подключение приложения к Mach-сервису расширения | принято, требование `anchor apple generic and certificate leaf[subject.OU] = "8625S77CSU" and identifier "com.facelessdiplomat.splitway"` выполняется |
| B. Запись и чтение | `0`, отпечаток совпал; элемент лежит в `/Library/Keychains/System.keychain` |
| B. Кто может расшифровать | только расширение. ACL элемента разрешает `decrypt` одному приложению — расширению; `security find-generic-password -w` и от пользователя, и от root через `sudo` ждёт окна авторизации |
| B. После обновления расширения | новая версия по новому пути `/Library/SystemExtensions/<UUID>/…` читает элемент. В ACL остался путь первой версии, то есть доступ сверяется по требованию к подписи, а не по пути |
| B. После перезагрузки | подключение приложения запускает процесс расширения, и оно читает элемент |
| B. Рабочая сборка после перезагрузки (2026-10-31) | Splitway закрыт, туннель «Весь трафик» включён системой (`scutil --nc start`): подключается за 2 с, внешний адрес отличается от прямого. Начала приватного ключа нет ни в `/Library/Preferences/com.apple.networkextension.plist`, ни открытым текстом в `/Library/Keychains/System.keychain` |
| C. Доставка | строка дошла, отпечаток совпал |
| C. Хранение | строка лежит открытым текстом в `/Library/Preferences/com.apple.networkextension.plist` с правами `-rw-r--r--`: её может прочитать любой пользователь Mac |

## Вывод

- **A** не работает для системного расширения.
- **C** работает, но приватный ключ на диске открыт всем пользователям Mac.
- **B** работает от root в песочнице, защищает элемент ACL и переживает обновление расширения и перезагрузку. Выбран B.

## Влияние на план

- M2-12: адаптеры — `NSXPCConnection` в приложении и `NSXPCListener` в расширении на `NEMachServiceName` с `setConnectionCodeSigningRequirement`, `SystemKeychainSecretStore` на `SecItem` с `kSecUseDataProtectionKeychain = false`. Кодек, требование к клиенту и сценарии уже есть в `SecretDelivery`.
- Расширение запускается по требованию: подключение приложения к Mach-сервису само поднимает его процесс, запускать туннель ради доставки не нужно.
- Риск: ACL элемента привязан к требованию подписи расширения, которое его создало. Расширение с другой подписью (сборка разработки → Developer ID) может не прочитать и не перезаписать старый элемент. `SystemKeychainSecretStore` должен уметь удалить недоступный элемент и создать новый; проверить на сборке Developer ID (M7).
- Не проверено: удаление и повторная установка расширения (нужно новое одобрение) и поведение с включённым SIP. SIP владелец проверяет на своём Mac (решение D-36), удаление — в M6-02.
