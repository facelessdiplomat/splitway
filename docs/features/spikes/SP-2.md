## Как проверяли

Сборка из ветки `spike/SP-2`: `FlowAttributionProbe` в системном расширении пишет в журнал для каждого потока:

- `sourceAppSigningIdentifier` из метаданных;
- процесс по audit token: signing identifier, Team ID, подпись Apple и путь (`SecurityCodeIdentityReader`);
- `remoteHostname` и адрес;
- взяла ли поток сессия.

Сессия работает как обычно, поэтому по последнему полю видно, узнал ли выбор приложение.

ВМ: macOS 26.6.2, сборка разработки, конфиг коммерческого провайдера (решение D-29) в режиме «Только выбранные приложения». Выбраны:

- Chrome, Firefox и VS Code (Electron) с официальных сайтов: подписи Google `EQHXZ8M8AV`, Mozilla `43AQ936H96` и Microsoft `UBF8T346G9`, Gatekeeper — «Notarized Developer ID»;
- апплет на CFNetwork (`NSData(contentsOf:)`);
- апплет с `WKWebView`.

Отдельное приложение на Swift с фоновой `URLSession` (загрузку выполняет `nsurlsessiond`) собрано уже после выбора и не выбиралось. Safari, `curl` и `ssh` тоже не выбирались: Safari не было в списке приложений, ошибка каталога исправлена.

Прогонов два:

1. с «исключить локальные сети» выключенным — проявилась ошибка DNS;
2. с включённым — DNS к резолверу ВМ шёл напрямую, и стали видны соединения TCP.

Ещё наблюдения:

- **DNS.**
  - Запросы, которые `mDNSResponder` отправляет за приложение, приходят UDP-потоками к системному резолверу (порт 53) с identifier и audit token приложения, а `remoteHostname` у них — запрашиваемое имя.
  - Chrome и VS Code отправляют запросы своим резолвером, тоже от своего имени.
  - Собственные запросы `mDNSResponder` приходят от `com.apple.mDNSResponder`.
- **Ошибка DNS в первом прогоне.** 393 запроса выбранных приложений ушли в туннель к резолверу ВМ `192.168.64.1` и остались без ответа. Firefox не открыл ни одного соединения TCP, у Chrome их было 2 из 255 потоков. В M4-11 это исправлено: запрос выбранного приложения теперь уходит на DNS туннеля (`DNSQueryRedirection`).
- **Системные службы** (`shazamd`, `parsecd`, `webprivacyd`, `passd` и другие) приходят от своего имени. У короткоживущих процессов (`GoogleUpdater`, `syspolicyd`, `timed`, `mobileassetd`) код по audit token уже не читается. Источник тогда неизвестен, и поток идёт напрямую, хотя identifier в метаданных есть.
- **Ответ `false`.** Потоки невыбранных приложений (`curl`, `ssh`, Safari, системные службы) уходили напрямую и работали.
- **QUIC.** Chrome отправляет QUIC (UDP, порт 443) от Google Chrome Helper. Разбор — в SP-6.

## Проверка исправлений

После исправлений M4-11 и каталога сборка из той же ветки прошла проверку в ВМ. «Исключить локальные сети» было выключено, выбраны Safari и оба апплета:

- Safari появился в списке приложений и выбирается;
- все 14 потоков Safari (7 соединений и 7 запросов DNS) ушли в туннель;
- запросы DNS апплетов получили ответ через туннель, и за ними открылись соединения;
- внешний адрес апплета отличается от адреса `curl`, который шёл напрямую.

## Вывод

- Атрибуция по audit token работает для всех проверенных приложений. Система передаёт поток от имени приложения, даже когда сеть за него ведёт WebKit, `mDNSResponder` или `nsurlsessiond`. Safari и WKWebView-приложения поддерживаются.
- Хелперы Chrome и Electron лежат внутри бандла приложения, и правило по пути выбранного приложения их покрывает.
- `remoteHostname` заполнен у приложений на системном резолвере и пуст у Chrome. Для Chrome повторный резолвинг имени через туннель не срабатывает, но его запросы DNS теперь сами уходят на DNS туннеля.
- DNS-запросы приложений приходят в transparent proxy. Нужен ли сверх этого `NEDNSProxyProvider`, решает SP-9.

## Влияние на план

- M4-04: пометка «не поддерживается» для Safari и WebKit-приложений не нужна. Safari теперь есть в списке: каталог не пропускает ссылку `/Applications/Safari.app` с флагом `hidden`.
- M4-09: потоки WebKit и `nsurlsessiond` приходят с audit token приложения. Риск: процесс, который завершился раньше, чем прочитан его код, неизвестен, и его поток идёт напрямую. Так может уйти мимо туннеля фоновая загрузка выбранного приложения, которое уже закрыто. Вариант — брать `sourceAppSigningIdentifier`, если код не читается. Identifier в метаданных даёт система, но у ad-hoc кода его выбирает автор, поэтому так можно узнавать только приложения с Team ID. Решить в M4-15.
- M4-13 и SP-9: прозрачный прокси уже перенаправляет DNS-запросы выбранных приложений. SP-9 проверит, что меняется при включённом `NEDNSProxyProvider`, и нужен ли он вообще.
- SP-6: QUIC Chrome приходит UDP-потоками Google Chrome Helper.
- Не проверено: Telegram (нужна загрузка), подтверждение на Mac владельца.
